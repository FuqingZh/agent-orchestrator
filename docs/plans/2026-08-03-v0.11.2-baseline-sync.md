# AO fork v0.11.2 baseline synchronization

Status: active

Date: 2026-08-03

Authority: [ADR 0003](../adr/0003-stable-upstream-baseline-sync.md)

## Goal

Make upstream `v0.11.2` the fork's auditable source baseline while preserving
the fork's shipped database history and only the five downstream capability
boundaries accepted by ADR 0002 and ADR 0003.

The completed source change must be suitable for an isolated canary. It does
not deploy or replace the host's installed AO binary.

| Input | Commit |

Refresh and verify all three remote objects before creating the synchronization

silently replace the target.

## Non-goals

- Do not restore Symphony or `WORKFLOW.md` scheduling.
- Do not add Linear write-back or make Linear a runtime state owner.
- Do not implement systemd/cgroup process containment.
- Do not enable AO project-level `autoMerge`.
- Do not alter the installed AO service, live database, Dashboard, nginx, or
  host rollback artifacts.
- Do not take unreleased upstream Linear pull requests as dependencies.

### Slice 2: reconcile the downstream delta

Audit `git diff v0.11.2...HEAD` and classify every runtime difference against
this allowlist:

1. GitHub App installation-token authentication;
2. daemon-only Linear credential filtering;
3. read-only, project-scoped Linear intake;
4. actionable bot review continuation; and
5. provider-update refresh for commented inline review threads.

Delete obsolete long-prompt delivery code now covered by upstream. Run the
focused tmux isolation reproduction against the merged tree and retain that
patch only if the failure still exists. Reject drive-by refactors and new
features during this slice.

Acceptance:

- every remaining runtime diff maps to one allowlisted boundary;
- each retained boundary has a focused behavioral test;
- worker tests prove Linear credentials are absent from tmux and ConPTY
  launches while the daemon-side adapter still receives its credentials;
- Linear tests prove project/assignee scoping, canonical issue identity,
  open-state filtering, and no tracker writes;
- bot feedback tests prove configured allow/deny behavior; and
- commented-review tests prove provider updates refresh the relevant thread
  without reopening unrelated feedback.

## Pull-request structure

1. Documentation PR: ADR 0003, this plan, and docs index.
2. Synchronization PR: pinned upstream merge, migration compatibility,
   downstream delta reconciliation, tests, and status updates.

The synchronization PR is intentionally one compatibility unit. New features,
process containment, and host deployment use separate decisions and pull
requests.

## Rollback and residual risk

Before merge, rollback is branch deletion with fork `main` unchanged. After
source merge, revert the synchronization merge only if no later fork commit
depends on it. Production rollback restores one captured binary, database, and
service generation; never mix generations.

The principal residual risks are migration-ledger mistakes, an upstream change
that subtly overlaps a retained adapter, and incomplete canary coverage for
host-specific runtime behavior. The migration matrix, downstream-diff audit,
and isolated canary are required specifically to bound those risks.
