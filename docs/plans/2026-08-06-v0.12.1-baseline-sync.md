# AO fork v0.12.1 baseline synchronization

Status: planned; source-only; no production deployment authorization

Date: 2026-08-06

Authority: [ADR 0003](../adr/0003-stable-upstream-baseline-sync.md) and
[ADR 0004](../adr/0004-explicit-upstream-main-snapshots.md)

## Goal

Merge the pinned upstream `v0.12.1` release into the fork without rewriting
published history, changing migrations already shipped by either lineage, or
silently retaining downstream behavior that upstream now supplies. The result
must be suitable for review and an isolated runtime canary.

This plan changes source and repository documentation only. It does not update
the installed AO binary, live database, user service, Dashboard, or private
host configuration.

## Ownership and cross-repository boundary

This repository owns the upstream merge, migration compatibility, downstream
patch reconciliation, generated artifacts, AO tests, and AO runtime canary.
The calibration repository owns portable adoption and instruction-transport
guidance in
`docs/implementation-plans/20260806-v2.5-ao-upstream-alignment-implementation-plan.md`.
Private host readiness and deployment evidence remain outside both public
repositories. Do not copy host paths, service state, or rollback material into
this plan.

## Non-goals

- Do not merge a later upstream `main` SHA in place of the pinned release.
- Do not rebase or force-push the fork's published history.
- Do not deploy, migrate, restart, or reconfigure the live AO installation.
- Do not fold upstream PR #3485 or PR #3550 into the baseline merge.
- Do not restore Symphony, workflow scheduling, or retired prompt workarounds.
- Do not add Linear write-back or make Linear an AO state owner.
- Do not enable always-on project `autoMerge` or infer production authority
  from a source merge.

## Execution graph

### Slice 0: accept the synchronization contract

Land this plan and its `docs/README.md` index entry before touching the source
baseline. Re-read the remote SHAs, upstream release status, PR #3485, and PR
#3550 immediately before implementation.

Acceptance:

- every pinned object resolves to the recorded commit;
- the plan links from the documentation index;
- source sync, portable calibration, private host readiness, and production
  deployment have distinct owners; and
- Markdown and repository whitespace checks pass.

### Slice 1: create an isolated merge branch

Create `codex/sync-upstream-v0.12.1` from the then-current fork `main`. Fetch
the exact tag and merge it with a normal `--no-ff` merge commit. Prefer upstream
core lifecycle behavior unless the downstream patch ledger explicitly owns the
conflicting contract. Do not implement unrelated cleanup while resolving
conflicts.

Acceptance:

- the branch starts from the freshly read fork `main`;
- `git merge-base --is-ancestor 1df40e93772c HEAD` succeeds;
- both published histories remain reachable; and
- every manual conflict resolution has a test or an explicit ledger owner.

### Slice 2: reconcile both migration lineages before runtime work

The fork has already shipped versions `0037` through `0044`. Upstream
`v0.12.1` adds different migrations at versions `0042`, `0043`, `0044`, and
`0047`, so filename uniqueness alone is not sufficient. Start with this
candidate source mapping, but do not accept it until the database matrix proves
schema and data convergence:

| Upstream source | Candidate fork path |
| --- | --- |
| `0042_review_run_unique_per_harness.sql` | `0045_review_run_unique_per_harness.sql` |
| `0043_add_session_pinned.sql` | `0046_add_session_pinned.sql` |
| `0044_backfill_review_run_batch_id.sql` | `0047_backfill_review_run_batch_id.sql` |
| `0047_agent_model_catalog.sql` | `0048_agent_model_catalog.sql` |

Preserve every previously shipped fork migration byte-for-byte. Preserve the
upstream source bytes when mapping a new migration and record source commit,
fork path, and SHA-256 in `docs/upstream-migration-map.md`.

A native `v0.12.1` database records versions `0042`, `0043`, `0044`, and
`0047` with meanings different from the fork's existing versions. Test that
lineage explicitly. If the candidate mapping skips required work, repeats a
non-idempotent operation, or produces a different schema or data state, add a
new append-only high-number reconciliation migration. Never edit an already
shipped migration to hide the collision.

The migration matrix must cover:

1. a fresh merged database;
2. upstream `v0.11.2` and native `v0.12.1` databases;
3. fork databases stopped after versions `0039`, `0041`, and `0044`;
4. the documented workstation version-`0040` collision lineage;
5. the current fork `main` schema with representative review, notification,
   session, and model-catalog data; and
6. a second migration pass with no further schema or data change.

Compare required tables, columns, indexes, triggers, constraints, and
backfilled values, not only the highest recorded version.

### Slice 3: audit the downstream patch ledger

Resolve source conflicts against current behavior and re-evaluate every
remaining fork delta against `v0.12.1`. The current candidates are:

1. GitHub App installation-token authentication;
2. daemon-only Linear credential filtering;
3. read-only, project-scoped Linear intake;
4. actionable bot-review continuation;
5. provider-update refresh for commented review threads; and
6. tmux integration-test isolation.

For each candidate, either retain it with focused behavioral evidence, retire
it because the release supplies an equivalent contract, or defer it with an
explicit reason and owner. Keep Symphony and the prior long-prompt workaround
retired. Record the resulting release baseline in `docs/downstream-patches.md`;
do not let an unexplained runtime diff survive the audit.

### Slice 4: regenerate owned artifacts and documentation

Regenerate SQL and API artifacts only from their owning source contracts. Run

Run the candidate daemon with an isolated `AO_DATA_DIR`, run file, ports, tmux

### Slice 6: deliver one compatibility-sensitive baseline PR

Deliver the merge, conflict reconciliation, migration compatibility, generated
artifacts, tests, and baseline documentation as one synchronization pull
request. Read CI, current-head review, and unresolved threads against the exact
head. Same-scope mechanical feedback may continue with bounded retries;
out-of-contract feedback returns to a new calibration decision.

Because the PR changes source and database compatibility, do not request merge
or auto-merge without fresh human authorization after the exact-head gate is
green. Merging the source PR still does not authorize deployment.

### Slice 7: validate and, if still needed, adopt the Codex prompt-file fix

After the baseline PR, use a separate branch and pull request for upstream PR
#3485. First re-read whether its commit has merged upstream or entered a stable
release. If not, cherry-pick or reimplement only its file-over-inline contract.

In addition to focused Go tests, run a real Codex black-box case through AO and
tmux using a repository `AGENTS.md` large enough to reproduce the observed
inline-command failure. Prove that:

- the staged instruction file, not the full instruction text, is present in
  Codex argv;
- fresh launch and restore both consume the intended instructions;
- task-prompt limits remain separate from system-instruction transport;
- a staging failure is reported instead of silently returning to the unsafe
  inline path; and
- no arbitrary byte or confidence threshold is introduced as a substitute for
  the transport fix.

Record the AO and Codex versions, instruction size, command-shape observation,
launch/restore result, and exact error for any failed case. Configuration
readback and mocked argv tests alone are not acceptance evidence.

### Slice 8: keep worker containment independent

### Slice 9: authorize production deployment separately

binary/database/service generation transactionally; never infer this authority

## Rollback and stop conditions

Before merge, abandon only the isolated synchronization branch; leave fork
`main` and the installed AO unchanged. After source merge, revert the merge
only if no later fork work depends on it. Production rollback is not covered by
this source plan.

Stop and preserve the branch when a pinned SHA changes, migration histories do
not converge, a downstream delta has no owner, an exact-head gate fails without
a same-scope fix, review expands the accepted contract, or host authorization
would be required. Report the actual boundary rather than weakening a test or
silently dropping compatibility.
