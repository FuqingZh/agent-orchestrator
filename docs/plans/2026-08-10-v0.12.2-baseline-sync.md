# AO fork v0.12.2 baseline synchronization and production update

Status: active; fork-only runtime changes archived; direct v0.12.2 source
synchronization in progress; production deployment is not authorized

Date: 2026-08-10

Authority: [ADR 0003](../adr/0003-stable-upstream-baseline-sync.md) and
[ADR 0004](../adr/0004-explicit-upstream-main-snapshots.md)

## Goal

Make the fork's source tree follow the pinned upstream `v0.12.2` stable release
without selectively carrying fork-only runtime behavior, while preserving
published history, converging every shipped SQLite lineage, and producing a
reviewed, isolated-runtime-verified source baseline from which a production
candidate can later be built.

This plan keeps three decisions separate:

1. the stable `v0.12.2` source synchronization;
2. any later explicitly pinned upstream `main` snapshot; and
3. production binary, database, service, and Dashboard cutover.

The complete fork history is archived at
`archive/fork-private-main-c55165a8` (`c55165a8b042715e6e613028d3d3039fff79d90f`)
and remains recoverable. The synchronization candidate is allowed to discard
fork-only runtime behavior, but it must retain immutable migration history and
the minimum compatibility checks required to upgrade databases that have seen
the fork line. Nothing in this document authorizes replacing the installed AO
generation.

## Ownership and delivery boundary

This repository owns the release merge, conflict reconciliation, migration
compatibility, downstream-patch audit, generated artifacts, repository tests,
exact-head review, and isolated runtime evidence.

Use one task-specific writer in one isolated worktree. Before mutation, verify
AO daemon health and authoritative ownership when AO lifecycle routing is
available; otherwise use the isolated-worktree fallback for this new work.
Never patch, stage, commit, or push a sibling owner's worktree.

Private host readiness owns installed paths, live database backup, service
configuration, process quiescence, rollback artifacts, and post-cutover
readback. Do not copy private host paths, credentials, service state, or
database material into this public plan.

## Non-goals

- Do not replace the pinned release with the observed upstream `main`.
- Do not cherry-pick selected post-release features into the stable baseline.
- Do not rebase or force-push the fork's published history.
- Do not edit any migration already shipped by either fork or upstream.
- Do not selectively restore fork runtime behavior after archival. The source
  of truth for runtime, API, frontend, and adapters is upstream `v0.12.2`.
- Do not remove or rewrite already-published SQLite migration history merely to
  make the tree textually identical to upstream; retain it only as migration
  compatibility, not as active fork behavior.
- Do not mix worker-process containment or durable runtime cleanup into the
  release synchronization.
- Do not install, restart, migrate, reconfigure, or otherwise touch the live AO
  binary, database, service, Dashboard, or Electron state.
- Do not infer merge or production authority from passing tests or CI.

## Affected contracts

| Surface | Owning source or evidence | Required outcome |
| --- | --- | --- |
| SQLite migrations and schema | immutable migration files, migration map, migration matrix | every fresh, fork, and native-upstream lineage converges without rewriting history |
| Storage and generated SQL | queries, schema, `sqlc` output | source and generated code agree on a clean second generation |
| Daemon HTTP and frontend API | controller DTOs, spec generator, OpenAPI, generated TypeScript | no API/schema drift and preserved fork compatibility |
| Session/workspace behavior | service, lifecycle, runtime, `workspace_files.go` tests | upstream release behavior plus explicitly retained fork contracts |
| Agent and reviewer adapters | shipped registry and adapter tests | release harnesses remain available without restoring test-only or retired paths |
| Desktop, Chat, browser, and Dashboard | frontend source, packaging checks, isolated canary | user-visible release surfaces start, persist, and recover from the merged source |
| Distribution metadata | CLI build metadata and release-repository configuration | candidate provenance and fork/upstream download ownership are explicit before deployment |
| Durable documentation | status, downstream ledger, migration map, verification record | the resulting baseline and residual risks are discoverable from `docs/README.md` |

### Slice 3: reconcile migration lineages before runtime work

The fork has immutable migrations through
`0049_reconcile_v0121_native_lineage.sql`. Upstream `v0.12.2` contains native
migrations at colliding versions `0047`, `0048`, and `0049`, then adds release
migrations through `0082`. The observed upstream `main` additionally occupies
`0054` and `0083` through `0085`.

Do not accept filename uniqueness or the highest recorded version as proof of
compatibility. Build a byte- and semantics-aware mapping for each colliding
upstream migration:

1. identify whether a shipped fork migration already represents the same
   operation;
2. preserve every shipped fork migration byte-for-byte;
3. preserve the upstream source bytes when a migration must be mapped to a new
   fork path;
4. choose any unshipped fork version only after re-reading both the stable tag
   and observed upstream-main ledger;
5. re-check that reservation immediately before merge; and
6. add a new append-only reconciliation migration only when the matrix proves
   that source mapping alone cannot converge all histories.

Update [`upstream-migration-map.md`](../upstream-migration-map.md) with source
commit, original path, mapped fork path, SHA-256, semantic ownership, and the
lineages for which the operation is already represented. Never edit an older
file to hide a collision.

The migration matrix must cover:

1. a fresh database created by the merged source;
2. the current fork `0049` database;
3. native upstream `v0.12.1` and `v0.12.2` databases;
4. fork databases stopped after versions `0039`, `0041`, and `0044`;
5. the documented workstation version-`0040` collision lineage;
6. representative session, review, notification, project, model-catalog, and
   Chat data;
7. foreign keys, indexes, triggers, constraints, and required backfills; and
8. a second migration pass with no further schema or data change.

Compare canonical schema and representative data, not only migration-version
rows. A native upstream database and a current fork database must reach the
same required merged contract.

Acceptance:

- every matrix row converges;
- mapped source hashes match the exact upstream files;
- all numeric versions are unique in the fork tree;
- no shipped migration changed; and
- any unresolved schema or data difference stops source integration.

### Slice 9: authorize and execute production cutover separately

Only a later explicitly authorized host-readiness and deployment task may

After explicit cutover authorization, quiesce active writers, stop the service,

do not improvise a forward fix against the live database.

4. A separately authorized production-readiness and cutover task with private
   rollback evidence.

## Rollback and stop conditions

Before merge, rollback means abandoning only the isolated synchronization
branch and preserving fork `main`, existing worktrees, and the installed AO.
After source merge, revert the merge only if no later fork work depends on it.
Production rollback is owned by the later host task, not by this source plan.

Stop and preserve the exact branch, head, owner, worktree, and evidence when:

- a pinned release or fork-base object changes without re-pinning;
- migration histories do not converge or a mapped source hash differs;
- a downstream delta has no owner or retirement evidence;
- generated artifacts drift after a second generation;
- a required local or exact-head gate fails without a same-contract fix;
- the isolated canary leaves resources or cannot prove a required release
  surface;
- independent review finds an unresolved compatibility regression;
- actionable review threads remain;
- ownership is ambiguous or more than one writer can mutate the branch;
- review expands beyond the accepted baseline contract; or
- production paths, credentials, service changes, or irreversible authority
  would be required.

Do not weaken a test, edit shipped history, absorb upstream `main`, or touch
production to manufacture progress.
